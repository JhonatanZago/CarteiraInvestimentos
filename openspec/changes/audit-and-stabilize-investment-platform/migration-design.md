# Desenho de migrations aditivas — TASK 1.3

## Situação encontrada

- O projeto usa `spring.jpa.hibernate.ddl-auto` (`update` em desenvolvimento e `create-drop` em testes).
- Não há Flyway, Liquibase ou diretório de migrations versionadas.
- `acao` já possui `moeda`, `listing_country_code`, `exchange`, `exchange_mic`, `logo_url` e `data_source`.
- `portfolio_snapshot` já possui índice `(carteira_id, data_hora)`, mas não há restrição de idempotência diária.
- `ativo_carteira` registra apenas quantidade, preço médio e data da primeira compra; não há câmbio ou operação individual.

## Migração proposta (PostgreSQL, somente aditiva)

### V001 — normalização de metadados de ativo

Verificar/ adicionar de forma idempotente as colunas nullable para permitir upgrade de bases antigas:

```sql
ALTER TABLE acao ADD COLUMN IF NOT EXISTS moeda varchar(3);
ALTER TABLE acao ADD COLUMN IF NOT EXISTS listing_country_code varchar(2);
ALTER TABLE acao ADD COLUMN IF NOT EXISTS exchange varchar(80);
ALTER TABLE acao ADD COLUMN IF NOT EXISTS exchange_mic varchar(12);
ALTER TABLE acao ADD COLUMN IF NOT EXISTS logo_url varchar(2048);
ALTER TABLE acao ADD COLUMN IF NOT EXISTS data_source varchar(40);
CREATE INDEX IF NOT EXISTS idx_acao_exchange_country ON acao(exchange, listing_country_code);
```

Backfill de `moeda` deve ser uma etapa explícita e auditável, nunca inferência cega pelo ticker. Registros não confirmados permanecem pendentes de revalidação.

### V002 — metadados de logotipo de corretora

### V003 — câmbio por operação (compatibilidade futura)

```sql
CREATE TABLE IF NOT EXISTS movimentacao_financeira (
  id bigint generated by default as identity primary key,
  carteira_id bigint not null references carteira(id),
  acao_id bigint not null references acao(id),
  corretora_id bigint not null references corretora(id),
  tipo varchar(16) not null,
  quantidade numeric(19,6) not null,
  preco_unitario numeric(19,8) not null,
  moeda varchar(3) not null,
  cambio_para_brl numeric(19,8),
  cambio_em timestamp with time zone,
  cambio_fonte varchar(80),
  valor_original numeric(19,8) not null,

CREATE INDEX IF NOT EXISTS idx_movimentacao_carteira_data ON movimentacao_financeira(carteira_id, data_operacao);

```

### V004 — idempotência de fechamento diário

```sql
CREATE UNIQUE INDEX IF NOT EXISTS uk_snapshot_daily_close
  ON portfolio_snapshot(carteira_id, ((data_hora AT TIME ZONE 'America/Sao_Paulo')::date), origem)
  WHERE origem = 'DAILY_CLOSE';
```

Antes de criar o índice, detectar e consolidar duplicidades em cópia da base; não apagar dados automaticamente em produção.

## Upgrade, rollback e validação

1. Fazer backup e restaurar em uma base de teste.
2. Aplicar V001–V004 em ordem e verificar constraints, índices e contagens.
3. Executar a aplicação em modo somente leitura e comparar endpoints antes/depois.
4. Rollback seguro: desabilitar o código consumidor, restaurar backup ou remover apenas índices/colunas novas após confirmação; nunca remover colunas existentes nem tabelas financeiras sem backup aprovado.
5. Para H2, manter o schema gerado pelo Hibernate nos testes; validar SQL PostgreSQL em pipeline de integração separado.

## Riscos e decisões

- `ddl-auto=update` não substitui migrations versionadas; deve ser desabilitado quando V001–V004 forem adotadas.
- Campos existentes em `acao` e `corretora` não devem ser recriados.
- Valores financeiros usam `numeric`/`BigDecimal`; nenhuma coluna `double`/`float` é aceitável.
- A tabela de movimentações é proposta para a fase 3; nesta task não é criada no banco nem altera os CRUDs atuais.
