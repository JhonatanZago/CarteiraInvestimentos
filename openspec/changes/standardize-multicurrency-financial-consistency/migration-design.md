# Additive Persistence Design — Task 1.3

## Scope

This document defines the persistence evolution for portfolio base currency and snapshot conversion provenance. It is a design artifact only: no migration is executed by this task, and no current entity or table is modified.

Current constraints verified from the repository:

- Hibernate generates H2 schemas for tests and uses `ddl-auto=update` in development.
- No Flyway or Liquibase migration directory is configured.
- `Carteira` has no base-currency field.
- `PortfolioSnapshot` stores aggregate values without currency or FX provenance.
- `MovimentacaoFinanceira` already preserves original value and optional BRL FX fields.
- `AtivoCarteira` already preserves the legacy estimated-conversion signal.

## Proposed additive schema

The following PostgreSQL-shaped statements are a future migration design, not commands to run in this task.

### V005 — portfolio base currency

```sql
ALTER TABLE carteira
  ADD COLUMN IF NOT EXISTS moeda_base varchar(3);
```

The column remains nullable during rollout. No default is assigned. Existing portfolios are `UNRESOLVED` until the base currency is explicitly proven and backfilled through an audited procedure.

### V006 — snapshot base aggregates and availability

```sql
ALTER TABLE portfolio_snapshot
  ADD COLUMN IF NOT EXISTS moeda_base varchar(3),
  ADD COLUMN IF NOT EXISTS total_investido_base numeric(19,8),
  ADD COLUMN IF NOT EXISTS patrimonio_atual_base numeric(19,8),
  ADD COLUMN IF NOT EXISTS resultado_base numeric(19,8),
  ADD COLUMN IF NOT EXISTS rentabilidade_base numeric(19,8),
  ADD COLUMN IF NOT EXISTS disponibilidade_monetaria varchar(16);
```

The existing `total_investido`, `patrimonio_atual`, `resultado`, and `rentabilidade` columns remain unchanged. New base-currency fields are nullable so old snapshots remain readable without being falsely reclassified as BRL.

### V007 — per-currency snapshot provenance

Mixed portfolios may require more than one conversion rate. A child table preserves each conversion context without overwriting the aggregate's original meaning:

```sql
CREATE TABLE IF NOT EXISTS portfolio_snapshot_cambio (
  id bigint generated by default as identity primary key,
  snapshot_id bigint not null references portfolio_snapshot(id),
  moeda_original varchar(3) not null,
  moeda_base varchar(3) not null,
  taxa_cambio numeric(19,8),
  cambio_efetivo_em timestamp with time zone,
  fonte_cambio varchar(80),
  disponibilidade varchar(16) not null,
  CONSTRAINT uk_snapshot_cambio_moeda
    UNIQUE (snapshot_id, moeda_original, moeda_base)
);
```

`AVAILABLE` requires a positive rate, effective timestamp, and source when the currencies differ. `ESTIMATED` requires an identifiable source and remains visibly non-definitive. `UNAVAILABLE` retains no fabricated rate and does not turn a missing conversion into zero.

## Safe backfill strategy

1. Take a backup and apply the additive schema to a copy of the database.
2. Populate `carteira.moeda_base` only where portfolio-level evidence is explicit and auditable.
3. Populate snapshot base fields only from a stored historical conversion or a documented identity conversion.
4. Create `portfolio_snapshot_cambio` rows only when the original currency and conversion state are known.
5. Leave portfolios and snapshots without evidence nullable and classified as `UNRESOLVED`.
6. Compare row counts, original monetary columns, foreign keys, and endpoint payloads before and after the trial migration.
7. Promote only after schema and data review; no automatic ticker inference, current-rate reconstruction, or deletion is allowed.

## Rollback

Rollback is application-first: stop consumers of the new nullable fields and restore the prior application artifact. Removing the additive columns/table is optional and only allowed after backup and confirmation that no deployment depends on them. Existing financial columns and rows are never deleted or rewritten as part of rollback.
